ZZW Code Teacher 最开始只是一个很朴素的想法：能不能做一个面向编程学习的桌面应用，把题目训练、代码编辑、提交评测、AI 教练、学习画像和教师管理放在同一个界面里。开发过程中，我把需求拆成一段段具体任务交给 TRAE，例如先做基础题库和编辑器，再做 AI 错误解释，之后继续补学习画像、讨论区、教师后台和整体 UI 美化。

比较有意思的是，很多原本看起来很复杂的功能，在和 TRAE 一轮轮对话后都变成了可执行的小步骤。比如 Avalonia 桌面端的三栏 IDE 布局、无边框圆角窗口、Material Design 风格的全局样式、AI 设置面板和提交历史复盘功能，都是通过不断描述体验目标、指出哪里“不够像产品”、再让 TRAE 调整实现细节完成的。它帮我跨过的最大障碍，是把一个“我脑子里有画面但还没成型”的教学工具，逐步落成了一个可以运行、可以演示、也方便继续迭代的 Demo。

## 1. Demo 简介

**是什么：**  
ZZW Code Teacher 是一款面向编程学习场景的桌面端代码教学 App，核心形态是“代码训练 IDE + AI 编程教练 + 学习画像 + 教师后台”的一体化系统。

**面向谁：**  
核心用户包括正在学习编程的学生、需要组织编程训练的老师，以及希望用 AI 辅助刷题、复盘错误、跟踪进度的学习者。

**主要功能：**

1. **编程训练与代码编辑**  
   学生可以在内置编辑器中选择题目、编写代码、运行样例、提交评测，并查看输出结果和历史提交。

2. **AI 教练辅助学习**  
   系统提供思路提示、错误解释、代码审查和自由提问能力，帮助学生在卡住时获得分层提示，而不是直接跳到答案。

3. **学习画像与教师管理**  
   学习画像展示提交数量、通过率、语言分布、难度分布、错题本、排行榜和复习任务；教师后台支持题目管理、提交管理、用户管理和班级管理。

## 2. Demo 创作思路

**灵感来源：**  
很多编程学习工具要么偏向在线判题，要么偏向代码编辑器，要么只是 AI 问答窗口。真实学习时，学生往往需要在多个工具之间切换：看题、写代码、跑样例、提交、读错误、问 AI、记录错题、复习、看学习进度。ZZW Code Teacher 的灵感，就是把这些分散动作收拢到一个更连贯的学习工作台里。

**想解决的问题：**

- 学生遇到错误时，不知道是语法问题、思路问题还是边界条件问题。
- 老师很难快速看到学生的练习进度、薄弱点和提交情况。
- 普通刷题工具缺少持续复盘机制，很多错题做完就忘。
- AI 工具虽然能回答问题，但如果脱离题目、代码和提交历史，帮助会比较碎片化。

**为什么做这个方向：**  
我选择做编程教学方向，是因为它天然适合 AI 参与，但又不能简单让 AI 代写答案。这个 Demo 的取舍是：把 AI 放在“教练”的位置，而不是“替你完成作业”的位置。系统更强调提示、解释、审查和复盘，让学生能逐步理解问题，同时让老师有数据可以判断学习效果。

## 4. TRAE 实践过程

**完整开发流程概览：**

1. **需求拆解与产品结构设计**  
   先让 TRAE 帮我把“AI 编程教练”这个想法拆成模块，包括登录、题库、编辑器、评测、AI 对话、学习画像、教师后台和博客讨论区。

2. **桌面客户端搭建**  
   使用 Avalonia 搭建桌面端主界面，形成顶部导航、主 IDE 三栏布局、底部状态栏和多页面切换结构。

3. **核心学习功能实现**  
   逐步实现题目浏览、代码编辑、样例运行、提交评测、提交历史、错题复盘、推荐题目和学习统计。

4. **AI 教练接入**  
   增加 AI 设置页，支持配置不同模型接口；在主界面中加入思路提示、错误解释、代码审查和自由提问。

5. **教师与社区功能扩展**  
   增加教师后台、班级管理、公告通知、讨论区、题解和知识广场，让 Demo 不只是个人刷题工具，也能覆盖教学组织场景。

6. **全局 UI 美化与体验打磨**  
   最后用 TRAE 对 UI 做全局 Material Design 风格重构，包括统一设计变量、磨砂玻璃卡片、无边框圆角窗口、菜单与下拉框风格、按钮反馈和交互动效。

## 6. 经验总结与踩坑复盘（可选）

这次做 ZZW Code Teacher 最大的体会是：AI 开发工具很适合把一个大想法拆成可执行的小任务，但前提是我要持续描述“我想要的体验是什么”。比如“界面更现代”这个说法太宽泛，真正有效的是继续补充“减少主界面按钮”“非核心功能放进二级菜单”“卡片要有毛玻璃质感”“下拉菜单主题不统一”等具体反馈。TRAE 在这种连续迭代里非常像一个耐心的搭档，可以快速修改、验证、再继续打磨。

踩坑比较多的地方是桌面端 UI 细节，比如无边框窗口、圆角窗口、弹出菜单、ComboBox 下拉层和透明窗口之间会互相影响。解决这些问题的过程也让我意识到，Demo 不只是“功能能跑”，还要关注用户真的点击时是否自然、按钮是否有反馈、菜单是否统一、弹窗是否挡住内容。这些细节虽然不一定是最复杂的代码，但会直接决定作品像不像一个完整产品。
